📘 Manual de Aprendizaje: Arquitectura & Seguridad Web

Guía didáctica sobre autenticación, autorización por ruteo, tokens JWT y buenas prácticas

1. Conceptos Fundamentales: Autenticación vs Autorización

En el desarrollo web es clave diferenciar ambos términos:

  • Autenticación (¿Quién sos?): Proceso para validar la identidad del usuario (ej. verificando credenciales).
  • Autorización (¿A qué tenés acceso?): Control de acceso para determinar si un usuario autenticado puede ejecutar una ruta o acción.

2. Modelos de Autenticación: Sesiones vs JWT

💡 ¿Por qué usamos JWT en arquitecturas modernas? HTTP es un protocolo sin estado (stateless). Para que el servidor reconozca al cliente en cada petición, usamos tokens firmados que el cliente adjunta en la cabecera Authorization: Bearer <token>.
Aspecto Sesiones en Servidor (Stateful) JWT Bearer Token (Stateless)
Almacenamiento El servidor guarda una tabla de sesiones activas. El servidor no guarda estado; valida la firma matemática del token.
Escalabilidad Requiere bases de datos compartidas (Redis) entre servidores. Cualquier nodo del backend valida el token con la clave secreta.
Decoupling (APIs) Depende de cookies vinculadas al dominio. Ideal para clientes React, mobile o servicios de terceros.

3. Autorización por Ruteo (Routing-Based Authorization)

💡 ¿Por qué Autorización por Ruteo? En lugar de dispersar condicionales dentro de cada controlador o vista, la autorización por ruteo declara los permisos directamente en la capa de transporte (rutas/endpoints). Esto garantiza que ninguna petición acceda a la lógica interna sin haber superado los filtros de acceso.

A. Backend: Interceptores de Ruta (Middlewares en Express)

Las rutas definen explícitamente su nivel de protección mediante middlewares encadenados:

// 1. Verificación de Firma JWT
export const verifyToken = (req: AuthRequest, res: Response, next: NextFunction) => {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) return res.status(401).json({ message: 'No token' });

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET as string);
    req.userId = decoded.id;
    req.userRole = decoded.rol_id;
    next();
  } catch {
    return res.status(401).json({ message: 'Invalid token' });
  }
};

// 2. Control de Acceso por Rol (RBAC)
export const requireRole = (roleId: number) => {
  return (req: AuthRequest, res: Response, next: NextFunction) => {
    if (req.userRole !== roleId) {
      return res.status(403).json({ error: 'Acceso denegado' });
    }
    next();
  };
};

// 3. Declaración en la Capa de Ruteo
import { Router } from 'express';
const router = Router();

// Autorización por Ruteo: requiere autenticación Y rol de Administrador (ID 1)
router.post('/moderacion/config', verifyToken, requireRole(1), moderationController.saveConfig);

B. Frontend: Protección de Rutas (React Router)

En el cliente, se utiliza el componente ProtectedRoute para envolver las vistas privadas en el enrutador impidiendo la carga desprotegida desde la URL:

// Componente Envoltorio ProtectedRoute
export const ProtectedRoute = ({ children, requiredRole }: { children: ReactNode, requiredRole?: number }) => {
  const { isAuthenticated, user, loading } = useAuth();

  if (loading) return <div>Cargando...</div>;
  if (!isAuthenticated) return <Navigate to="/login" replace />;
  if (requiredRole && user?.rol_id !== requiredRole) return <Navigate to="/unauthorized" replace />;

  return <>{children}</>;
};

// Enrutador Principal (AppRouter.tsx)
export const AppRouter = () => (
  <Routes>
    <Route path="/login" element={<LoginPage />} />

    {/* Autorización por Ruteo en Frontend */}
    <Route path="/admin" element={
      <ProtectedRoute requiredRole={1}>
        <AdminDashboardPage />
      </ProtectedRoute>
    } />
  </Routes>
);
